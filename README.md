# 通用项目工程文档模板

本目录是一套可复制到新项目仓库根目录的工程治理模板。它解决四类问题：

1. `AGENTS.md`：告诉编码 Agent **如何在本仓库安全、正确地工作**。
2. `ARCHITECTURE.md`：说明系统 **由什么组成、如何协作、边界在哪里**。
3. `docs/*.md`：沉淀跨模块的长期工程规范。
4. `docs/**/`：记录会持续增长的设计决策、产品规格、执行计划、生成文档和外部参考资料。

## 使用方式

将本目录中的文件复制到项目根目录，然后完成以下初始化：

- 全局搜索 `{{`，替换所有 `{{PLACEHOLDER}}`。
- 删除与项目技术栈无关的示例命令和规则。
- 在 `AGENTS.md` 中填入经过验证、可直接执行的构建和测试命令。
- 在 `ARCHITECTURE.md` 中填入真实模块、依赖方向、数据流和部署拓扑。
- 为首个核心功能建立 `docs/product-specs/` 规格和必要的 `docs/design-docs/` 设计文档。
- 将文档链接检查、测试、静态检查和安全扫描接入 CI。

建议用以下命令查找仍未替换的占位符：

```bash
rg -n '\{\{[A-Z0-9_]+\}\}' .
```

## 文档职责速查

| 文档 | 回答的问题 | 主要读者 | 更新时机 |
| --- | --- | --- | --- |
| `AGENTS.md` | 在仓库中工作时必须遵守什么、运行什么命令？ | Agent、开发者 | 命令、目录或协作规则变化时 |
| `ARCHITECTURE.md` | 系统有哪些组件，边界和依赖关系是什么？ | 全体研发 | 架构边界、数据流或部署方式变化时 |
| `docs/DESIGN.md` | 工程设计如何评审和记录？ | 设计者、评审者 | 设计流程或标准变化时 |
| `docs/FRONTEND.md` | 前端代码和体验如何保持一致？ | 前端研发 | 前端栈或约定变化时 |
| `docs/PLANS.md` | 跨阶段工作如何规划、跟踪和归档？ | 项目负责人、执行者 | 计划机制变化时 |
| `docs/PRODUCT_SENSE.md` | 产品决策遵循什么原则？ | 产品、设计、研发 | 产品原则变化时 |
| `docs/QUALITY_SCORE.md` | 如何量化交付质量和准入门槛？ | 全体研发 | 质量门槛变化时 |
| `docs/RELIABILITY.md` | 系统如何达到可用性和可恢复性目标？ | 后端、SRE、运维 | SLO、告警或容灾策略变化时 |
| `docs/SECURITY.md` | 安全边界、控制措施和响应流程是什么？ | 全体研发、安全人员 | 威胁模型或安全控制变化时 |
| `docs/design-docs/` | 某项重要技术方案为什么这样设计？ | 研发、评审者 | 方案提出、决策或实现偏离时 |
| `docs/product-specs/` | 用户问题、范围和验收标准是什么？ | 产品、设计、研发、测试 | 产品需求变化时 |
| `docs/exec-plans/` | 一项复杂工作如何分步落地？ | 实施者、评审者 | 执行过程中持续更新 |
| `docs/generated/` | 哪些内容由工具生成且不可手改？ | 研发、工具链 | 生成源或生成器变化时 |
| `docs/references/` | 外部规范的本地快照和来源是什么？ | 研发、Agent | 上游版本更新时 |

## 核心边界

- `AGENTS.md` 不应复制整份架构说明；它只保留 Agent 执行任务时需要立即知道的约束，并链接到详细文档。
- `ARCHITECTURE.md` 不记录临时任务进度；任务进度属于 `docs/exec-plans/`。
- 产品规格描述“为什么做、做什么、如何验收”，设计文档描述“技术上如何做、为何这样取舍”。
- `docs/generated/` 中的文件只能由声明的生成命令更新，不能人工修补。
- `docs/references/` 中的第三方内容不是本项目规范本身；引用时应标注来源、版本和许可证。
- 新项目初始化时只复制模板文件，不复制上个项目的已填写值、执行计划、凭证或生成快照；详见 `AGENTS.md` 的“上下文隔离与指令来源”。

## 推荐维护规则

- 文档与代码在同一个 PR 中更新。
- 所有相对链接必须通过 CI 校验。
- 过期规则应删除或明确标记，不保留互相矛盾的“历史说明”。
- 每份长期文档应标明负责人或责任团队、最后核验日期。
- 重大架构决策使用设计文档或 ADR 留痕，不只存在于聊天记录中。
