# 执行计划规范

负责人：`{{DELIVERY_OWNER}}`  
最后核验：`{{YYYY-MM-DD}}`

执行计划用于让跨阶段、高风险或多人协作的工作可追踪。计划描述“如何实施和验证”，不代替产品规格、架构说明或技术设计。目录见 [exec-plans/README.md](exec-plans/README.md)。

## 何时需要计划

- 需要多次提交、跨模块或跨团队协调。
- 涉及数据迁移、发布窗口、兼容期或回滚。
- 关键路径存在尚未验证的依赖或风险。
- 预计实施超过 `{{PLAN_THRESHOLD}}`，或负责人认为需要阶段性验收。

## 计划必须包含

- 项目、分支/版本、负责人、创建时间、状态。
- 背景、目标、非目标和完成标准。
- 现状与影响范围，包括代码、数据、接口、配置和运行环境。
- 分阶段任务，按依赖顺序排列，每项可验证。
- 验证命令、测试范围、发布方式、回滚或前滚方案。
- 风险、外部依赖、决策记录和阻塞项。
- 实际进度、与原计划的偏差及最终结果。

## 状态流转

```text
草案 -> 已批准 -> 执行中 -> 已完成
                  └------> 已取消
执行中 -> 已阻塞 -> 执行中
```

状态变更应记录日期和原因。完成时将文件从 `active/` 移到 `completed/`，保留历史，不重写成“仿佛从未变更”的计划。

## 命名和更新

- 文件名使用 `YYYY-MM-DD-简短主题.md`，例如 `2026-10-17-order-migration.md`。
- 每个工作阶段结束时更新进度、验证证据和下一步。
- 计划中出现新架构决策时，另写设计文档并链接；不要把临时计划当成永久架构事实。
- 已知技术债进入 [tech-debt-tracker.md](exec-plans/tech-debt-tracker.md)，并有清理条件和负责人。
